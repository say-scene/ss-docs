# 02. 새 노드 vLLM 기동 13분 — EBS lazy loading

> 상태: **원인 확인, 개선 미정** · 발생: 2026-10-27

## 증상

llm-v2 AMI로 새 노드를 띄워 vLLM이 Ready가 되기까지 **13분 20초**가 걸렸다. 가중치를 AMI에 넣어 기동을 빠르게 하려던 의도와 반대 결과다.

## 측정

첫 기동(새 노드)과 같은 노드에서 `rollout restart`한 재기동을 비교했다. 시각은 Pod conditions(`lastTransitionTime`)와 vLLM 로그 기준.

| 구간 | 첫 기동 (새 노드) | 재기동 (같은 노드) |
|---|---|---|
| Pod 생성 → NodeClaim 생성 | 1초 | — |
| 노드 준비 (EC2 부팅·조인·Ready) | 1분 8초 | — |
| Pod 네트워크 생성 | 17초 (CNI 재시도 1회 포함) | 2초 |
| 컨테이너 시작 → vLLM 엔진 시작 | 약 2분 33초 | 26초 |
| 가중치 로딩 (`Loading weights took`) | **322.8초** | **1.09초** |
| 워밍업·컴파일 | 3분 39초 | 1분 15초 |
| **PodScheduled → Ready** | **12분 11초** | **2분 1초** |
| **전체** | **13분 20초** (10:22:00 → 10:35:20) | 2분 1초 (10:40:00 → 10:42:01) |

참고로 같은 가중치를 빌더에서 HF로 받을 때는 약 135MB/s(8.06GB, 70초)였다. 첫 기동의 가중치 읽기는 약 20MB/s였다.

## 원인

AMI 스냅샷에서 만든 EBS 볼륨은 블록을 **처음 읽을 때 S3에서 가져온다**(lazy loading). 가중치뿐 아니라 미리 받아 둔 이미지 레이어(Python·torch 라이브러리)와 워밍업 중 읽는 파일도 같은 볼륨이라 모두 느려졌다.

- 재기동에서 엔진 시작·워밍업도 함께 빨라졌다. 재기동은 새 컨테이너라 컴파일 캐시가 남지 않으므로, 차이는 파일 첫 읽기 비용으로 본다.
- 재기동의 가중치 1.09초는 디스크가 아니라 **노드 페이지 캐시**에서 읽은 값이다. 재기동 2분 1초는 "같은 노드 + 메모리 캐시"의 최선값이다.
- Karpenter 노드는 매번 새로 만들어지고 매일 stop/start하므로, 실사용에서는 첫 기동 비용(약 10분)을 매번 낸다.

## 함께 확인된 값

- 메모리: 재기동 기준 `Model loading took 9.24 GiB`. 첫 기동의 16.75GiB는 로딩 중 집계로 보인다. KV cache 8GiB를 더해도 limit 28Gi 이내.
- CPU: `VLLM_CPU_OMP_THREADS_BIND=auto`가 물리 코어 4개 중 3개(`core ids=[4, 5, 6]`)를 추론에, 1개(`reserved_cpus=[7]`)를 예약했다.

## 개선 후보

| 후보 | 내용 | 비고 |
|---|---|---|
| 기동 시 S3(또는 HF)에서 가중치 받기 | 새로 쓰는 블록은 lazy loading 영향이 없음 | 빌더 실측 135MB/s 기준 1~2분 예상 (추정) |
| 이미지를 레지스트리에서 pull | 이미지 레이어도 첫 읽기 비용을 피함 | ECR 미러 필요 여부 검토 |
| Fast Snapshot Restore | lazy loading 자체 제거 | AZ당 시간 과금, 실습 비용 부담 |
| `--safetensors-load-strategy=prefetch` | vLLM 로그가 안내한 옵션 | 효과 미측정 |

개선 후에도 같은 표 형식으로 첫 기동·재기동을 측정해 비교한다.

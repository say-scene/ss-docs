# vLLM 부하 분석 및 관측 추적 기록

> 담당 ① · 작성 2026-11-03 · 갱신 2026-11-03 (알람 규칙 6회 수정 반영) · 상태: **측정 진행 중 (슬롯 32 까지)**

슬롯 수를 어떻게 정했고 왜 그 알람을 그렇게 만들었는지를, **틀렸던 과정까지 포함해** 남긴다. 필수항목 ⑥(부하 변화 측정) · ⑦(장애 재현·원인 분석) · ⑨(문서화) 근거를 겸한다.

부하를 거는 방법은 [loadtest/vllm-concurrency-loadtest-v1.md](../loadtest/vllm-concurrency-loadtest-v1.md) 참조. 이 문서는 **측정 결과와 해석**을 다룬다.

**읽는 규칙**

```
날짜가 붙은 절   그 시점의 사실. 설정이 바뀌면 낡는다
날짜가 없는 절   원리와 추론. 바뀌지 않는다
```

측정값은 날짜만으로 부족하다. **프롬프트 길이가 병목 위치를 바꾸므로**(2.6) 조건을 함께 적는다.

## 2. 부하 시험 결과

> 2026-11-02 21:00 ~ 2026-11-03 17:10. 각 측정의 조건이 다르면 비교할 수 없다.

### 2.1 조건

```
구간        2026-11-03 10:20 ~ 10:37
설정        --max-num-seqs 1
워크로드     입력 약 240토큰 / 출력 128토큰
            finished_reason 100% length
```

### 2.2 결과

| 지표 | 값 |
|---|---|
| 처리량 한계 | 20.5 요청/분 (0.34 req/s) |
| 동시 처리 | 1건 |
| 포화 시작 | 동시 2건째부터 |
| 최대 대기 | 7건 (11:00 구간 15건) |
| e2e p50 / p95 | 25초 / 30초 이상 |
| TTFT p50 / p95 | 21초 / 37초 |
| TPOT p50 / p95 | 20ms / 47ms — 부하와 무관 |
| GPU 사용률 | 80~100% 톱니 |
| KV 캐시 사용률 | 2~3% |

### 2.3 검산

세 지표가 독립적으로 같은 값을 가리킨다.

```
리틀의 법칙  (running 1 + waiting 7) / 0.34 req/s = 23.5초
실측 e2e p50                                      = 25초

생성 토큰 44 tok/s / 0.34 req/s = 129 토큰/요청  = max_tokens 128
입력 토큰 82 tok/s / 0.34 req/s = 241 토큰/요청  = 입력 p95 490 과 정합
```

### 2.4 포화 원인

```
reason=capacity   7 -> 15      슬롯 없음
reason=deferred   0 고정        스케줄러 정책 아님
KV 캐시 사용률     2~3%          자원 제약 아님
preemption        0건           선점 없음
```

`--max-num-seqs 1` 이 원인이다. GPU 연산·KV 캐시·토큰 예산은 모두 배제되었다.

### 2.5 병목의 성격

```
TTFT  60ms -> 21초    350배      대기 시간
TPOT  23ms -> 20ms    변화 없음   생성 속도는 그대로
```

느림의 원인은 대기이지 연산이 아니다. 이 구분이 처방을 가른다.

| 보이는 것 | 뜻 | 처방 |
|---|---|---|
| TTFT 증가, TPOT 유지 | 줄을 섬 | 동시 처리 늘리기 |
| TTFT 유지, TPOT 증가 | GPU 공유 | 자원 늘리기 |
| 둘 다 증가 | 심각한 포화 | 둘 다 |
| 둘 다 유지, e2e 증가 | 생성 토큰 증가 | 설계 검토 |

### 2.6 슬롯별 부분 관측

> 2026-11-03. 슬롯 수를 1 -> 32 로 올리며 재시험이 진행 중이다. 전체 결과는 아직 없다.

| 시각 | 슬롯 | 입력 tok/s | 생성 tok/s | 동시 실행 | 대기 | TTFT | KV | 선점 |
|---|---|---|---|---|---|---|---|---|
| 11-03 10:20~10:37 | 1 | 82 | 44 | 1 | 7 | 21초 | 2~3% | 0 |
| 11-03 (시각 미기록) | 8 | 3063 | 38 | 8 | 7 | 2.658초 | 34.66% | 0 |
| 11-03 16:24:43 | 16 | 2809 | 20 | **6** | 5 | 4.665초 | **97.06%** | 0 |
| 11-03 16:24:43 (재전송) | 16 | 3640 | 66 | 14 | 9 | 2.385초 | 94.02% | 0 |
| 11-03 17:03:13 | 32 | 1336 | 704 | 32 | 32 | 4.373초 | 71.52% | 0 |

세 번째·네 번째 행은 **같은 발화의 두 전송**이다. `StartsAt` 이 같고 값만 다르다 — annotation 이 평가마다 다시 렌더링되기 때문이다.

**슬롯 1 행만 계획된 시험 구간이고, 나머지는 알림 메시지에서 읽은 단일 시점 값이다.** 프롬프트 길이를 고정하지 않아 입력이 82 ~ 3640 tok/s 로 제각각이다.

**① 같은 대기열 길이(7건)에서 TTFT 가 8배 줄었다.** 2.4 의 "병목은 슬롯"이라는 결론과 방향이 맞는다. 다만 부하 조건이 달랐으므로 슬롯 효과라고 단정할 수는 없다(아래 참고).

**② 슬롯 16 의 첫 줄이 중요하다.** 슬롯이 10개 남는데 5건이 기다린다. **병목이 슬롯에서 KV 캐시로 넘어갔다.** 그 조건에서는 슬롯을 더 올려도 소용없다. 이 관측이 "대기가 있으면 슬롯이 꽉 찬 것"이라는 전제를 깼다(7.6 ④).

**②-1 슬롯 32 는 정반대다.** 32/32 로 슬롯이 먼저 찼고 KV 는 71.52% 로 여유가 있다. 입력이 1336 tok/s 로 짧아진 덕이다. **같은 클러스터에서 프롬프트 길이만 달라져도 병목이 KV 에서 슬롯으로 옮겨간다.**

```
입력 2809 tok/s, 동시 6건   → KV 가 먼저 참   (프롬프트 김)
입력 1336 tok/s, 동시 32건  → 슬롯이 먼저 참  (프롬프트 짧음)
```

생성 처리량도 슬롯 1 의 44 tok/s 에서 704 tok/s 로 16배다. 역시 프롬프트 길이가 달라 슬롯 효과라고 단정할 수 없다.

**③ 선점은 다섯 경우 모두 0 이다.** vLLM 이 "쫓아내기" 대신 "안 받기" 로 버티고 있다. 선점이 0 을 벗어나는 지점이 메모리가 진짜 한계인 경계다.

#### 프롬프트 길이는 잡음이 아니라 두 번째 축이다

위 네 줄은 입력 토큰이 82 ~ 3640 tok/s 로 제각각이라 비교가 성립하지 않는다. **프롬프트 길이가 시험 설계 변수인데 고정하지 않았기 때문이다.**

그런데 단순히 고정하고 잊을 변수도 아니다. **프롬프트 길이가 병목이 어디에 생기는지를 결정한다.**

```
KV 사용량 ≈ 동시 시퀀스 수 × 시퀀스당 토큰 수
            └ 슬롯이 정함      └ 프롬프트 길이가 정함
```

```
짧은 프롬프트 + 슬롯 많음   슬롯이 먼저 참  → 슬롯이 병목
긴 프롬프트  + 슬롯 많음   KV 가 먼저 참   → KV 가 병목
```

데이터가 그대로 보여준다.

```
슬롯 8  : 동시 8건, KV 34.66%   →  시퀀스당 4.3%
슬롯 16 : 동시 6건, KV 97.06%   →  시퀀스당 16.2%
```

**시퀀스당 KV 가 3.7배다.** 슬롯이 늘어서가 아니라 프롬프트가 그만큼 길었던 것이다.

> 그 프롬프트 길이에서는 **슬롯을 16으로 올려도 6건밖에 못 돌린다.** KV 가 먼저 막는다. 실효 동시성은 `--max-num-seqs` 가 아니라 KV 가 정한다.

`--max-num-seqs` 를 몇으로 둘지는 **프롬프트 길이를 정해야 답이 나온다.**

#### 그래서 시험은 2차원이어야 한다

```
              프롬프트 짧음    프롬프트 김
슬롯 1
슬롯 4
슬롯 8
슬롯 16
```

각 칸에서 볼 것:

```
동시 실행 수가 슬롯 수에 닿는가     닿으면 슬롯이 병목
KV 가 먼저 100% 에 가는가          가면 KV 가 병목
선점이 0 을 벗어나는가             벗어나면 메모리가 진짜 한계
```

**경계선이 그려진다.** 어느 프롬프트 길이까지는 슬롯을 올리는 게 효과가 있고, 어디부터 소용없는지가 보인다.

판단 보류. 이 표를 채우면 비교표를 만든다.

## 3. 발견한 문제

> 2026-11-03 기준. ss-be 쪽은 아직 전달 전이라 그대로 남아 있다.

### 3.1 `/api/v1/report` 가 20~26초

```
측정   http_server_requests_seconds_max{uri="/api/v1/report"}
       status=502  20초  (09:29)
       status=200  26초  (09:32)
비교   turn / lookup / translate 는 전부 1초 미만
검산   26초 / TPOT 23ms = 약 1,130 토큰
```

대화 전체를 읽고 요약·교정을 생성하는 작업이므로 설계상 느린 것이 맞다.
결함이 아니다. 다만 SLI 를 대화 경로와 분리해야 한다.

### 3.2 20초 대기 후 502

```
근거   해당 구간 finished_reason = stop 100%, length 0건
       -> 토큰 한도 초과가 아님
       -> ss-be 스키마 검증에서 거부
결론   INVALID_REPORT_RESPONSE
유력   corrections.size() != users.size()
```

사용자는 20초어치 생성을 기다린 뒤 아무 결과도 받지 못한다.

### 3.3 해당 502 경로는 로그를 남기지 않는다

```java
error(502, "INVALID_REPORT_RESPONSE", ...)        // 로그 없음
error(502, "INCOMPLETE_STRUCTURED_RESPONSE", ...) // 로그 없음
error(502, "INVALID_INFERENCE_RESPONSE", ...)     // 로그 없음
```

`kubectl logs | grep` 결과가 비어 있었다.
지표가 없었다면 이 장애를 감지할 수단이 없었다.
알람을 `status="502"` 기준으로 걸어야 하는 직접적 근거다.

### 3.4 실패 모드가 둘

```
2026-11-02 부하시험   length 18건/분  -> INCOMPLETE_STRUCTURED_RESPONSE  토큰 한도
2026-11-03 실사용     stop + 거부     -> INVALID_REPORT_RESPONSE         스키마
```

원인은 다르나 증상(20초 이상 대기 후 502)과 비용이 같다.

## 4. 관측 방법론

> 날짜 없음 — 지표의 성질이라 설정이 바뀌어도 그대로다.

### 4.1 추적의 구조

```
1  이상한 숫자를 본다
2  이것이 사실이면 무엇이 참이어야 하는지 묻는다       가설
3  그 가설만 참/거짓으로 갈라놓는 지표를 고른다        핵심
4  던진다. 가설이 죽으면 2로 돌아간다
```

지표를 많이 보는 것이 아니라 가설을 구분하는 지표 하나를 고르는 작업이다.

### 4.2 지표를 믿기 전에 확인할 것

```
p95 는 상위 5%를 버린다
  요청 30건 중 26초짜리 1건은 p95 에 나타나지 않는다. 드문 느림은 _max 로 본다

histogram_quantile 은 없는 정밀도를 만든다
  버킷 경계 사이를 선형 보간한다. le=10 다음이 le=30 이면 11초가 17초로 그려진다

모집단이 다르면 비교가 성립하지 않는다
  같은 p95 라는 이름으로 서로 다른 요청 집합을 재고 있을 수 있다

Gauge 는 스크레이프 순간만 본다
  30초 간격에 2초짜리 요청은 대부분 관측되지 않는다
  "있었는가" 는 Counter, "지금 몇 개인가" 는 Gauge
```

### 4.3 읽는 요령

```
불가능한 순서가 보이면     시스템이 아니라 쿼리를 의심한다
                         ss-be < vLLM 은 구조상 성립할 수 없다
p50 과 p95 가 붙으면      요청량을 함께 확인한다
                         균일해서인지 요청이 없어서인지 뜻이 정반대다
선이 끊기면               장애가 아니라 트래픽 0 일 수 있다
                         rate 가 0 이면 분위수는 NaN 이 된다
빈 결과도 데이터다         빈 grep 결과가 3.3 을 찾아냈다
지표 이름을 믿지 않는다     DCGM_FI_DEV_GPU_UTIL 은 커널이 실행된 시간의 비율이며
                         연산 용량 사용률이 아니다
로컬 체크아웃은 git 이 아니다  근거로 삼기 전에 어느 시점의 파일인지 확인한다
```

### 4.4 지표와 질문의 대응

| 질문 | 사용할 지표 |
|---|---|
| ss-be 가 vLLM 밖에서 시간을 쓰는가 | `_sum / _count` (평균) |
| 어느 엔드포인트가 느린가 | `histogram_quantile` + `by (uri)` |
| 가장 오래 기다린 요청은 | `_max` |
| 줄을 서는가, GPU 를 나눠 쓰는가 | TTFT vs TPOT |
| 왜 대기하는가 | `vllm:num_requests_waiting_by_reason` |
| 자원이 모자란가 | `vllm:kv_cache_usage_perc`, `vllm:num_preemptions_total` |

### 4.5 추적 순서

```
1  증상을 숫자 하나로 고정한다
2  라벨로 쪼갠다                 by (uri)
3  보간 없는 지표로 확인한다       _max, _sum/_count
4  다른 축에서 같은 사건을 본다    finished_reason, status, reason
5  코드로 구조를 확인한다
6  가설을 반박할 데이터를 찾는다   "틀렸다면 무엇이 보여야 하는가"
```

4번이 이번 추적의 결정타였다. 시간 축만 보다가 `finished_reason` 축으로
옮기자 원인이 바로 갈렸다.

## 5. 추적 중 폐기한 가설

> 날짜 없음 — 추론 기록이다.

| 가설 | 반박 근거 |
|---|---|
| GPU 사용률 100% 이므로 연산 포화 | 지표 정의가 커널 실행 시간 비율. 용량이 아님 |
| GPU 때문에 running 이 1 | running 2 여도 100% 로 표시됨. 상관과 인과를 혼동 |
| 콜드 스타트 때문에 느림 | 두 번째 요청이 더 느렸음 (20초 -> 26초) |
| p95 모집단 희석 때문 | 개수가 반대였음 (ss-be 4.2 < vLLM 6.2 건/분) |
| 매니페스트는 2인데 클러스터가 1 | 로컬 체크아웃이 뒤처진 것. origin/main 도 1 |
| KV 캐시 블록 부족 | 사용률 2~3%, preemption 0건 |

설명이 매끄러울수록 검증을 건너뛰기 쉽다.
매번 "이 가설이 틀렸다면 데이터에 무엇이 보여야 하는가" 를 물어야 한다.

## 6. 대시보드 상태

> 2026-11-03 기준.

### 6.1 작동하는 패널

```
요청량 / 처리량 / 응답시간 p95 / 오류건수
CPU / 메모리 / GPU 사용률
vLLM 처리중·대기 / vLLM 요청량 / 토큰 처리량
TTFT / TPOT / 요청당 토큰 수
```

### 6.2 수리 필요

### 7.1 지표를 고르기까지 — 폐기한 안 셋

| 안 | 폐기 이유 |
|---|---|
| GPU 사용률 80% | `DCGM_FI_DEV_GPU_UTIL` 은 커널이 돌던 시간의 비율이다. 작은 커널 하나로도 100% 가 된다. 11-03 아침 사람 한 명이 쓸 때도 100% 를 찍었다 |

| 슬롯 가동률 80% (분모 = 실측 최대) | `--max-num-seqs` 를 내리면 분모가 며칠간 옛 값으로 남는다. 완전 포화에서도 임계를 못 넘어 **침묵한다** |

두 번째는 적용 후 실측으로 확인됐다. 슬롯 8 부하 시험에서 받은 알림이다.

```

```

입력이 생성의 80배다. "생성 토큰 80%" 로 걸었다면 38 tok/s 는 바닥이라 **이 포화를 놓쳤을 것이다.**

공통 원인은 하나다.

> **비율은 분모를 요구하고, 분모는 설정에 묶이고, 설정은 변한다.**

거짓 발화는 시끄러워서 알아채지만 침묵은 알아챌 방법이 없다. 그래서 비율을 버리고 **절대값(TTFT 초)** 으로 갔다. 가동률은 조건에서 빼고 메시지의 숫자로만 남겼다. `대기 7건` 은 `--max-num-seqs` 가 무엇이든 뜻이 같다.

### 7.2 규칙

```yaml
alert: VllmTtftHigh
expr:  rate(vllm:time_to_first_token_seconds_sum[5m])
       / rate(vllm:time_to_first_token_seconds_count[5m]) > 1.2
for:   2m
labels:
  severity: warning
annotations:
  summary: "vLLM 첫 토큰 지연 — 5분 평균이 기준 1.2초를 2분 연속 초과"
```

**왜 응답시간이 아니라 TTFT 인가.** 응답시간에는 생성 길이가 섞인다.

```
응답시간 = 큐 대기 + prefill + 생성
TTFT     = 큐 대기 + prefill
```

`/api/v1/report` 는 토큰을 1,100개쯤 만드느라 설계상 20초가 걸린다. 응답시간 기준이면 정상인데도 늘 울린다. TTFT 는 생성 길이를 빼고 보므로 **긴 요청과 밀린 요청을 가른다.**

**왜 분위수가 아니라 평균인가.** `histogram_quantile` 은 버킷 경계 사이를 직선 보간해 없는 정밀도를 만든다. 이 히스토그램은 1.0 다음 경계가 2.5, 그다음 5.0 이라 그 구간이 성기다. `_sum / _count` 는 누적 초를 누적 건수로 나눈 값이라 보간이 없다.

버킷 천장은 2560초다. 애초 우려했던 "분위수가 최상위 버킷에 막힌다" 는 해당 없었다. 평균을 택한 근거는 **보간**과 **모집단**(5분에 30건이면 p95 는 위에서 1.5번째) 둘로 줄었다.

**왜 1.2초인가.**

```
평상시    0.06초
부하 시   20초
```

300배 차이라 임계를 어디에 둬도 틀리기 어렵다. 1.2초는 평상시의 20배다.

`/api/v1/report` 는 프롬프트가 길어 큐가 비어도 prefill 만으로 0.5~0.7초가 걸릴 수 있다. 5분 평균이라 묻히지만(30건 중 report 2건이면 평균 0.1초), report 만 연속으로 쓰는 경우를 대비해 1.0 이 아니라 1.2 로 뒀다.

**왜 `sum()` 으로 합치지 않는가.** 식이 파드별로 시리즈를 낸다. 합치면 `namespace`·`pod` 라벨이 사라져 Alertmanager 의 `group_by: [alertname, namespace]` 가 묶을 게 없어지고, 메시지에서 파드 이름도 빠진다. 롤링 교체 중 두 파드가 뜨면 `group_by` 가 메시지 하나에 두 줄로 묶어준다.

### 7.3 알림 메시지

```
[FIRING:1] VllmTtftHigh
WARNING · vllm
vLLM 첫 토큰 지연 — 5분 평균이 기준 1.2초를 2분 연속 초과

🔴 10.240.0.33:8000 / vllm-qwen-54c7847674-94k8x · 16:24:43 발화
첫 토큰 4.665s (5분 평균 · 평상시 60ms)
동시슬롯 최대 6/16 · 대기 최대 5건
KV 캐시 최대 97.06% · 선점 0회
생성 평균 20 tok/s · 입력 평균 2809 tok/s · GPU sayscene-gpu-wsl

읽는 법
대기 0 → vLLM 밖의 원인 (모델 로딩, 네트워크 등)
슬롯 꽉참 → 슬롯 부족. --max-num-seqs 올리기
슬롯 여유인데 대기 → KV 캐시가 막은 것. --max-model-len 줄이거나 GPU 증설
선점 > 0 → KV 부족으로 요청을 되돌림. 메모리가 한계라 슬롯을 올리면 더 나빠짐
```

**숫자 블록과 해석 블록을 빈 줄로 나눈다.** 받을 수 있느냐를 결정하는 넷(슬롯·대기·KV·선점)을 이웃한 두 줄로 모으고, 그 아래에 분기를 적는다. 조치할 설정 이름까지 넣어 메시지만 보고 무엇을 만질지 알 수 있다. 이렇게 하게 된 경위는 7.6 에 있다.

```
🟢 10.240.0.162:8000 / vllm-qwen-fbf996cd6-qdl2d 16:11:43 해소
```

#### 줄마다 맡은 질문

```
슬롯대기        포화인가?          예 / 아니오
생성·입력       무엇 때문인가?      긴 답변 / 긴 프롬프트
KV 캐시·선점    메모리 문제인가?    예 / 아니오
```

| 읽은 값 | 병목 | 조치 |
|---|---|---|
| 대기 0 | vLLM 밖 | 모델 로딩 중, 네트워크 등 |
| 대기 > 0, 슬롯 꽉참 | 슬롯 | `--max-num-seqs` 올리기 |
| 대기 > 0, 슬롯 여유 | KV 캐시 | `--max-model-len` 줄이거나 GPU 증설 |
| 선점 > 0 | 메모리가 이미 한계 | 슬롯을 올리면 더 나빠진다 |
| 생성 tok/s 우세 | 긴 답변 | 설계 검토 |
| 입력 tok/s 우세 | 긴 프롬프트 | 프롬프트 축소 검토 |

**`대기 > 0, 슬롯 여유` 행이 7.6 ④ 로 추가됐다.** 그 전에는 "대기가 있으면 슬롯이 꽉 찬 것"으로 보고 이 경우를 두지 않았다.

**선점(preemption)** 은 KV 캐시가 모자라 처리 중이던 요청을 중단하고 큐로 되돌린 횟수다. 되돌린 요청은 나중에 처음부터 다시 생성하므로 그때까지의 GPU 작업이 버려진다. 0 이 아니면 병목이 슬롯이 아니라 메모리이고, 그 상태에서 `--max-num-seqs` 를 올리면 더 나빠진다.

**생성과 입력을 더하면 안 된다.** prefill 은 수백 토큰을 한 번에 행렬 연산으로 밀어넣어 토큰당 싸고, decode 는 하나씩이라 비싸다. 오늘 포화 지점 둘로 거칠게 역산하면 `생성 토큰 1개 ≈ 입력 토큰 64개` 어치다. 정밀한 모델이 아니라 "자릿수가 다르다"는 감각으로만 쓴다.

#### 집계 방식을 숫자마다 적는다

| 값 | 표기 | 왜 |
|---|---|---|
| 첫 토큰 | 5분 평균 | 알람 조건과 같은 값이어야 한다 |
| 슬롯·대기 | 최대 | 포화는 가장 심했던 순간으로 판단한다 |
| 생성·입력 | 평균 | 처리 속도는 평균이 맞다 |
| KV 캐시 | 최대 | 메모리 압박도 최대로 판단한다 |
| 선점 | 5분 증가분 | 횟수라 누적이다 |

1번째 줄의 `(5분 평균)` 이 창 길이를 한 번 알리고, 나머지 줄은 같은 창 안에서 평균이냐 최대냐만 구분한다. 이렇게 하게 된 경위는 7.6 에 있다.

#### summary 와 description 의 역할

```
summary      규칙 — 무엇을 넘었나 (고정)
description  측정 — 지금 얼마인가 (파드별)
```

Discord 템플릿이 `summary` 를 `CommonAnnotations` 로 읽는다. 그룹의 모든 알람이 같은 값일 때만 채워지므로, **값을 넣으면 두 파드가 다르게 발화할 때 그 줄이 통째로 사라진다.** 그래서 숫자는 전부 `description` 에 둔다.

#### 슬롯 분모는 설정값이 아니다

```promql
max(max_over_time(vllm:num_requests_running[24h]))
```

최근 24시간 관측 최대값이다. **설정값을 읽는 게 아니라 "이만큼까지 올라간 적이 있다"를 본다.**

창을 늘려도 안전한 이유: 설정을 바꾸면 Deployment 스펙이 바뀌어 **파드가 새로 뜨고, 새 파드는 새 시계열이라 옛 최대값을 물려받지 않는다.** 창은 파드 수명 안으로 자동으로 잘린다. 폐기한 `[7d]` 안이 "설정을 내리면 옛 분모가 며칠 남는다"로 깨졌던 것과 달리, 여기서는 파드 교체가 초기화해 준다.

처음에는 `[1h]` 이었다. KV 가 막으면 한 시간 내내 슬롯이 한도까지 안 올라가 분모가 작아지고, `6/6` 처럼 보여 **꽉 찬 것으로 오독된다.** 길수록 진짜 한도를 관측할 기회가 많다.

여전히 **관측값이지 설정값이 아니다.** 파드가 뜬 뒤 한 번도 한도까지 간 적이 없으면 작게 보인다.

**이 분모를 `expr` 에 쓰지 않는 이유**가 7.1 의 세 번째 폐기 사유다. 표시용으로는 틀려도 글자가 어긋날 뿐이지만, 조건에 쓰면 포화에도 침묵한다.

#### 노드 이름

`DCGM_FI_DEV_GPU_UTIL` 의 `hostname` 라벨에서 조회한다. vLLM 지표에는 노드 라벨이 없어 Discord 템플릿의 폴백이 파드 IP 까지 떨어지기 때문이다.

ServiceMonitor 에 relabeling 으로 `node` 라벨을 붙이는 방법도 있으나, **라벨이 바뀌면 시계열의 정체성이 바뀌어 기존 데이터가 끊긴다.** 부하 시험 데이터를 계속 비교하는 중이라 택하지 않았다.

#### 파드 IP 와 파드 이름

```
🔴 10.240.0.162:8000 / vllm-qwen-fbf996cd6-qdl2d
   └─ 긁은 주소          └─ 파드 이름
```

`instance` 가 Service 가 아니라 파드 IP 인 이유: **ServiceMonitor 는 Service 를 파드 목록 조회에만 쓰고, 긁을 때는 각 파드에 직접 간다.** Service 를 거치면 어느 파드를 긁었는지 알 수 없다.

```
ss-be        → Service ClusterIP → (LB) → 파드    주소 고정
Prometheus   → Service 로 목록만 → 파드 직접      파드별 구분
```

추적에 쓸 값은 파드 이름 쪽이다. IP 는 재생성마다 바뀌고, 파드 이름은 ReplicaSet 해시를 품고 있어 **어느 설정 버전인지** 알려준다.

```
dbbfcc4b9   슬롯 8
fbf996cd6   슬롯 16
```

해시가 다르면 Deployment 스펙이 바뀐 것이다. 단순 재시작이면 해시는 같고 뒤 문자열만 바뀐다.

### 7.4 발화부터 도착까지

11-03 10:25 부하 시험 기준.

| 시각 | 일 | 어디서 |
|---|---|---|
| 10:25:00 | 부하 시작 | — |
| 10:27:00 | 5분 평균이 1.2초 돌파 → pending | Prometheus |
| 10:29:00 | 2분 연속 유지 → firing, 전송 | Prometheus → Alertmanager |
| 10:29:30 | 🔴 1통 | Discord |
| 10:30~10:43 | 계속 firing, 재전송 없음 | — |
| 10:43:30 | 🟢 1통 | Discord |

```
체감 지연   4분 30초
메시지 수   시험 한 번당 2통 (발화 · 해소)
```

지연의 내역이 중요하다.

```
5분 창이 차는 시간   2분 00초
for: 2m             2분 00초
group_wait: 30s     0분 30초
```

**`for` 를 줄여도 2분까지만 단축된다.** 더 빠르게 하려면 `[5m]` 창을 줄여야 하고, 그러면 거짓 발화 여유가 줄어든다.

```
5분 창에 30건 중 20초짜리 1건  →  (29×0.06 + 20)/30 = 0.73   안 울림
2분 창에 12건 중 20초짜리 1건  →  (11×0.06 + 20)/12 = 1.72   울림
```

해소도 같은 관성이 있다. 부하가 끝난 뒤 2분쯤 더 firing 상태로 있다가 해제된다.

#### 발화 시각

Prometheus annotation 에는 시각 함수가 없다. Alertmanager 템플릿에서 넣는다.

```
{{ .StartsAt | tz "Asia/Seoul" | date "15:04:05" }}
```

`tz` 는 Alertmanager v0.26+ 함수다. 컨테이너 시간대가 UTC 라 그대로 쓰면 9시간 어긋난다. 환경변수 `TZ` 를 넣는 방법도 있으나 StatefulSet 변경이라 파드가 재시작된다. `tz` 는 설정 재로드만으로 끝난다.

`.StartsAt` 은 **`for` 를 채워 firing 이 된 시각**이다. 조건이 처음 참이 된 시각(`ActiveAt`)이 아니고, 둘의 간격이 정확히 `for` 값이다. `ActiveAt` 은 Alertmanager 로 전달되지 않으므로 필요하면 Prometheus 에서 조회한다.

```promql
ALERTS_FOR_STATE{alertname="VllmTtftHigh"}   # pending 이 시작된 유닉스 시각
```

평소에는 Discord 가 찍는 도착 시각과 `group_wait` 만큼(30초)밖에 차이가 없다. 값어치는 다른 데 있다 — **업무시간 밖에 발화해 아침 9시에 도착한 알림**에서는 실제 발생 시각을 알 길이 없었다.

### 7.5 적용 전 검증

Explore 에서 확인한 것.

| | 항목 | 쿼리 | 결과 |
|---|---|---|---|
| ① | 지표 이름 존재 | `count by (__name__) ({__name__=~"vllm:time_to_first_token.*"})` | 통과. `_bucket` 23, `_sum` 1, `_count` 1 |
| ② | 식의 값과 발화 구간 | A: 식 그대로 / B: 식 `> 1` | 통과. 임계 아래에서 B 선 없음, 넘으면 나타남 |
| ③ | 버킷 천장 | `sum by (le) (..._bucket)` | 2560초. 천장 문제 없음 |
| ④ | 무트래픽 동작 | `rate(..._count[5m]) * 60` | 0/0 = NaN → 안 울림 |
| ⑤ | 평상시 거짓 발화 | `vLLM 처리 중` 패널 09:15~10:15 | 대기 0. TTFT 60ms. 발화 조건 미달 |
| ⑥ | 실제 발화 | 슬롯 8 부하 시험 | 통과. 슬롯 분모가 8 을 자동으로 잡음 |

**①이 가장 중요하다.** 이름이 틀린 규칙은 에러를 내지 않고 빈 결과를 돌려준다. 조용히 아무것도 안 한다. 이번 vLLM 버전에서 `vllm:time_per_output_token` → `vllm:inter_token_latency` 로 바뀐 전례가 있었다.

**쿼리 B 의 성질.** PromQL 의 `> 1` 은 비교가 아니라 걸러내기다. 조건이 거짓인 시점은 결과에서 빠져 점이 없어진다. 그래서 **B 에 선이 그려진 구간이 곧 발화 구간**이고 눈으로 읽힌다. 알람 식을 적용 전에 검증하는 가장 간단한 방법이다.

⑤는 TTFT 평균을 그 구간에 직접 돌린 것이 아니라 대기열이 0 임을 확인한 간접 증거다. 큐가 비면 TTFT 는 prefill 뿐이고 그 값이 60ms 로 측정됐으므로 같은 결론이지만, 직접 측정은 아니다.

### 7.6 적용 후 고친 것

설계 단계에서는 안 보이고 **실제 알림을 받아야 보이는 문제**가 셋 나왔다.

#### ① 이름이 원인을 단정했다

처음 이름은 `VllmQueueLatency` 였다. 조건은 TTFT 인데 이름은 큐를 말한다. 큐가 아닌 이유로도 울릴 수 있고 메시지 마지막 줄이 그 경우를 안내하므로, **이름과 조건이 어긋나 있었다.**

```
VllmQueueLatency   원인을 추정한 이름
VllmTtftLatency    Time 과 Latency 가 겹치고, 높다/낮다가 없다
VllmTtftHigh       측정하는 값 + 그 상태        <- 채택
```

Prometheus 관례도 상태로 끝난다(`NodeDiskFillingUp`, `KubeCPUOvercommit`, `TargetDown`). 나중에 TTFT 에 관한 다른 알람을 추가해도 이름이 겹치지 않는다.

이름을 바꾸면 Alertmanager 는 **다른 알람으로 취급한다.** 적용 시점에 firing 중이었다면 🟢 옛 이름 해소와 🔴 새 이름 발화가 따로 온다.

#### ② 창이 섞여 메시지가 거짓말을 했다

적용 첫날 이런 알림을 받았다.

```
첫 토큰 10.64s (5분 평균)
동시처리슬롯: 0/8 · 슬롯대기: 0건
GPU : 생성 97 tok/s · 입력 178 tok/s
KV 캐시 0%
```

마지막 줄의 안내(`대기 0 이면 vLLM 밖의 원인`)대로 읽으면 **틀린 결론**에 도달한다.

원인은 창 길이가 섞여 있던 것이다.

```
창(5분)   첫 토큰 · 생성 · 입력        rate(...[5m])
순간      슬롯 · 대기 · KV             max(vllm:num_requests_running)
```

생성 97 tok/s 가 0 이 아니라는 게 **그 5분 안에 분명히 부하가 있었다**는 증거다. 알림이 도착한 시점에 이미 끝났을 뿐이다.

이건 예외가 아니라 정상 동작이다. **체감 지연이 4분 30초이므로 알림이 뜰 때쯤 짧은 부하는 이미 끝나 있다.** 순간값은 대부분 쓸모없는 시점을 가리킨다.

셋을 `max_over_time(...[5m])` 로 바꿔 다섯 줄이 모두 `[t-5m, t]` 를 보게 했다.

```
수정 전   동시처리슬롯: 0/8 · 슬롯대기: 0건 · KV 캐시 0%
수정 후   동시처리슬롯: 최대 8/8 · 슬롯대기: 최대 7건 · KV 캐시 최대 41%
```

> **교훈.** 알림에 여러 지표를 담을 때는 집계 창을 먼저 맞추고 표기한다. 창이 다른 숫자를 나란히 놓으면 읽는 사람이 같은 순간이라고 가정한다. **지연이 큰 알람일수록 순간값은 위험하다.**

한 번의 annotation 렌더링 안에서 `$value` 와 모든 `query` 는 같은 평가 시각으로 실행된다. 끝점은 원래 같았고, **길이만 어긋나 있었다.**

#### ③ 해소 줄로 파드를 구분할 수 없었다

```
🔴 10.240.0.162:8000 / vllm-qwen-fbf996cd6-qdl2d · 16:04:13 발화
🟢 10.240.0.241:8000 15:38:43 해소                              ← 파드 이름 없음
```

파드 IP 는 재생성마다 바뀐다. 이름이 없으니 **같은 파드인지 다른 파드인지 판단할 수 없었다.** (실제로는 슬롯 8 파드가 해소되고 슬롯 16 파드가 발화한 것이었다.)

발화 줄과 같은 형식으로 맞췄다.

```
🟢 10.240.0.241:8000 / vllm-qwen-dbbfcc4b9-kvfsn 15:38:43 해소
```

`{{ if .Labels.pod }}` 로 감싸 `pod` 라벨이 없는 알람(`NodeDiskFillingUp` 등)에는 영향이 없다.

#### ④ 전제가 틀렸다 — 슬롯이 남는데도 대기가 생긴다

슬롯 16 으로 올린 뒤 이런 알림을 받았다.

```
동시슬롯 최대 6/16 · 대기 최대 5건
KV 캐시 최대 97.06% · 선점 0회
생성 평균 20 tok/s · 입력 평균 2809 tok/s
```

**슬롯이 10개 남는데 5건이 기다린다.**

이 문서와 설계 과정에서 반복해 쓴 전제가 있었다.

> `waiting > 0` 이면 슬롯이 꽉 찬 것이다. vLLM 은 슬롯이 비면 즉시 `running` 으로 올리니까.

**틀렸다.** 슬롯 말고도 받지 못하는 이유가 있다.

```
KV 캐시 부족           이번 경우. 97% 라 새 시퀀스를 받을 블록이 없다
토큰 예산 부족          --max-num-batched-tokens 512
```

입력 2809 tok/s · 생성 20 tok/s 가 경위를 말해 준다. **긴 프롬프트가 쏟아져 KV 를 채웠고, 슬롯이 놀아도 받을 수 없게 됐다.** 선점이 0 인 것은 vLLM 이 "쫓아내기" 대신 "안 받기" 로 버티는 중이라는 뜻이다. 더 밀어붙이면 선점이 시작된다.

어느 쪽인지는 이 지표로 갈린다.

```promql
vllm:num_requests_waiting_by_reason     # legend {{reason}}
```

**이 전제가 영향을 준 곳이 둘이다.**

```
슬롯 분모의 근거   "대기가 쌓이면 running 이 곧 한도" -> 성립하지 않는다
                  창을 24시간으로 늘려 완화했다 (7.3)
메시지 마지막 줄   "대기 0 이면 vLLM 밖의 원인" 하나뿐이라
                  이 경우를 안내하지 못했다 -> 읽는 법 블록으로 교체
```

> **교훈.** 반례가 나오기 전까지 전제는 검증되지 않은 채로 설계에 스며든다. 이 전제는 슬롯 1·8 에서는 참이었다. **참인 구간에서만 관측하면 전제가 틀린 줄 모른다.**

#### ⑤ 원인이 눈에 들어오지 않았다

④의 알림에서 원인(KV 97%)과 증상(슬롯 여유인데 대기)이 **두 줄 떨어져 있고 사이에 토큰 줄이 끼어 있었다.** 읽는 사람이 직접 이어야 했다.

```
첫 토큰 4.665s
동시처리슬롯: 최대 6/16 · 슬롯대기: 최대 5건     ← 증상
GPU ... : 생성 평균 20 tok/s · 입력 평균 2809 tok/s
KV 캐시 최대 97.06% · 선점 0회                   ← 원인
대기 0 이면 vLLM 밖의 원인                        ← 이 경우를 안내 못 함
```

받을 수 있느냐를 결정하는 넷을 이웃한 두 줄로 모으고, 빈 줄 뒤에 분기를 적었다.

```
동시슬롯 최대 6/16 · 대기 최대 5건
KV 캐시 최대 97.06% · 선점 0회

읽는 법
...
슬롯 여유인데 대기 → KV 캐시가 막은 것. --max-model-len 줄이거나 GPU 증설
```

**세 번 눈이 움직이면 끝난다.** 여유 있는 슬롯 옆에 97%, 그 아래 줄이 둘을 이어 준다.

> **교훈.** 알림에 여러 지표를 담을 때는 **같은 질문에 답하는 숫자를 붙여 놓는다.** 순서만 바꿔도 읽는 비용이 달라진다. 그리고 해석 블록에는 조치할 설정 이름을 적는다 — 메시지에서 행동까지 거리가 짧아진다.

#### ⑥ 해소와 발화가 한 통에 담겼다

```
🔴 10.240.0.162:8000 / vllm-qwen-f9b7f6f76-hsmsc · 17:03:13 발화
...
🟢 10.240.0.33:8000 / vllm-qwen-54c7847674-94k8x 16:50:13 해소
```

파드를 바꿀 때마다 나왔다.

```
파드 교체
  옛 파드의 시계열이 사라짐 -> 그 알람 해소
  새 파드가 뜨고 부하가 걸림 -> 그 알람 발화
  둘이 13분 차 -> 한 통
```

**Prometheus 는 해소를 15분간 계속 Alertmanager 에 보낸다.** 그 15분은 소스 상수(`resolvedRetention`)라 설정으로 바꿀 수 없다.

```yaml
global:
  resolve_timeout: 5m      # 이건 다른 것. 바꿔도 효과 없다
```

`resolve_timeout` 은 `EndsAt` 없이 도착한 알람을 해소로 치는 기준이다. Prometheus 는 `EndsAt` 을 항상 붙여 보낸다.

**같은 파드면 중복되지 않는다.** Alertmanager 는 라벨 집합으로 알람을 식별하므로, 같은 파드가 해소됐다가 다시 발화하면 같은 항목이 갱신될 뿐이다. **라벨이 달라질 때만** — 즉 파드가 바뀔 때만 둘이 별개 알람이 된다.

그래서 묶는 기준에 `pod` 를 넣었다. vLLM 에만 건다.

```yaml
routes:
  - receiver: discord
    matchers: [namespace = "vllm"]
    group_by: [alertname, namespace, pod]
    active_time_intervals: [business-hours]
```

전역 `group_by` 에 넣으면 `Kube*` 알람들도 파드별로 쪼개져 알림 수가 늘어난다. 잃는 것은 없다 — `replicas 1` + `Recreate` 라 두 파드가 동시에 발화할 수 없다.

#### 곁가지 — 파드 IP 는 재사용된다

```
16:04:13 발화   10.240.0.162 / vllm-qwen-fbf996cd6-qdl2d
17:03:13 발화   10.240.0.162 / vllm-qwen-f9b7f6f76-hsmsc
```

**같은 IP, 다른 파드다.** IP 만 보면 같은 파드로 착각한다. ③에서 해소 줄에 파드 이름을 넣은 것이 실제로 값어치를 했다.

### 7.7 운영

```
Sync        ArgoCD 수동 Sync 필요. 푸시만으로는 적용되지 않는다
확인        kubectl -n monitoring get prometheusrule kube-prometheus-stack-vllm-latency \
              -o jsonpath='{.spec.groups[0].rules[0].alert}'
재로드 확인  kubectl -n monitoring logs prometheus-...-0 -c config-reloader --tail=20
이력 조회    ALERTS{alertname="VllmTtftHigh"}
            alertstate 라벨로 pending / firing 구간이 갈린다
            평상시에는 결과가 비는 것이 정상이다
```

`kube-prometheus-stack-vllm-latency` 는 **파드가 아니라 `PrometheusRule` 리소스**다.

```
values.yaml 의 맵 키 "vllm-latency"
  ↓ Helm 이 리소스를 만든다      이름 = <릴리스 이름>-<맵 키>
PrometheusRule
  ↓ prometheus-operator 가 규칙 파일로 만든다
Prometheus 가 다시 읽는다        파드 재시작 없음
```

**부하 시험 중에는 Silence 를 건다.** 의도한 부하에 알림이 오는 것은 잡음이다. Grafana → Alerting → Silences 에서 `alertname = VllmTtftHigh` 로 건다. 규칙을 끄는 것이 아니라 알림만 막는다.

**임계값은 데이터로 조정한다.** 2주쯤 돌린 뒤 `ALERTS` 이력을 본다. 평상시에 울렸으면 올리고, 부하 때만 울렸으면 둔다. 1.2초는 관측 두 점(0.06초와 20초) 사이에서 고른 값이지 평상시 평균을 직접 재서 정한 값이 아니다.

**이 알람이 잡지 않는 것.**

```
vLLM 중단   요청이 사라져 0/0 = NaN 이 되므로 조건이 거짓이 된다
            부하 중에 죽으면 오히려 해소(🟢) 메시지가 온다
            평상시에 죽으면 아무 메시지도 없다
            감지하려면 up{job="vllm-qwen"} == 0 알람이 따로 필요하다
            모델 로딩에 몇 분 걸리므로 for 는 5분 이상이어야 배포마다 울지 않는다
```

**슬롯을 바꾸는 것은 서비스 중단을 동반한 배포다.**

```yaml
replicas: 1
strategy:
  type: Recreate       # GPU 가 한 장이라 두 파드가 동시에 못 뜬다
startupProbe:
  periodSeconds: 10
  failureThreshold: 180   # 모델 로딩에 최대 30분 허용
```

옛 파드를 먼저 죽이고 새로 띄우므로 그 사이 `ss-be` 가 502 를 받는다. **부하 시험 중에 무심코 Sync 하면 그 회차가 날아간다.**

### 7.8 설정 파일 두 개의 역할

```
prometheus/values.yaml     언제 firing 이 되는가    expr, for, 메시지 본문
alertmanager/values.yaml   누구에게 어떻게 보내나    Discord, 시간대, 묶음 주기, 발화 시각
```

규칙 파일에는 Discord 라는 단어가 없다. 알림이 안 올 때 어느 쪽을 볼지 나누는 기준이 된다.

```
조건이 거짓인가           prometheus/values.yaml 과 Explore
조건은 참인데 안 보내나    alertmanager/values.yaml
                         (business-hours, group_wait, repeat_interval)
```

평일 09~19시(Asia/Seoul) 밖에 발화하면 버려지지 않고 보류됐다가 아침 9시에 온다. 그 전에 해소되면 오지 않는다.

`additionalPrometheusRulesMap` 의 구조는 세 층이다.

```yaml
additionalPrometheusRulesMap:
  vllm-latency:            # ① 맵 키 → PrometheusRule 리소스 하나. 정리용 이름
    groups:
      - name: vllm-latency # ② 그룹 → 평가 단위
        rules:
          - alert: ...     # ③ 실제 조건
```

`labels` 는 기계용(Alertmanager 의 라우팅·묶음), `annotations` 는 사람용(메시지 본문)이다. `severity` 를 annotations 에 넣으면 메시지에 안 나오고, 긴 설명을 labels 에 넣으면 값마다 별도 알람으로 묶여 폭주한다.

---

### 7.9 곁가지 — `KubeCPUOvercommit`

`additionalPrometheusRulesMap` 과 무관하다. 차트가 기본으로 주는 약 100개 규칙 중 하나다.

```
전체 파드의 CPU requests 합 > (클러스터 allocatable - 가장 큰 노드)
```

노드 하나가 죽으면 파드를 다 못 올린다는 뜻이다. 노드 수가 고정이면 구조적으로 항상 참이라 계속 온다. 끄려면 `additionalPrometheusRulesMap` 이 아니라 이쪽이다.

```yaml
defaultRules:
  disabled:
    KubeCPUOvercommit: true
```

끄면 자원이 정말 빠듯해져도 알려주지 않는다. 2026-11-03 기준 미결.

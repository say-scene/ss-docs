# vLLM 슬롯 1·2·4·8·16·32 누적 대화 부하 실험 통합 정리

- 실험일: 2026-11-03, KST(Asia/Seoul)
- 정리 범위: 슬롯 1·2·4·8·16·32. 슬롯 16은 C1·8·16·32·64, 슬롯 32는 C1·16·32·64·128을 측정. C는 동시 요청 수
- 자료: 터미널 결과 TXT, 기존 실험 PDF, 대화에 첨부된 Grafana 캡처
- 성격: 실제 수행한 탐색 실험의 기록. 서비스 전체의 수용 인원이나 최적 설정을 확정하는 용량 인증 결과는 아님.

## 1. 핵심 요약

1. **슬롯을 늘리면 일부 조건의 처리량이 개선됐지만, 모든 조건에서 지연이 줄지는 않았다.** 새 슬롯 1→2의 C2 처리량은 2.235→3.464 req/s, p95는 1.093→0.819초였다. 동시 요청 4에서 슬롯 2→4의 처리량은 3.497→6.586 req/s로 증가했다. 슬롯 4→8에서는 같은 조건의 처리량이 6.586→6.320 req/s로 소폭 감소했다.
2. **동시 요청 1·2·4는 대부분 300초 전에 문맥 한도 오류로 종료됐다.** 누적 대화를 초기화하지 않아 요청 문맥이 길어졌기 때문이다. 이 오류를 GPU OOM이나 KV 캐시 부족으로 해석하면 안 된다.
3. **동시 요청 8 이상은 성능 비교에 채택한 각 실험에서 300초를 채웠지만 응답 지연이 커졌다.** 슬롯 8, 동시 요청 32는 4.063 req/s, 성공 E2E p50 8.155초, p95 15.646초였다. 요청 실패가 없다는 것만으로 사용자 경험이 양호하다고 판단할 수 없다.
4. **슬롯 8의 동시 요청 16→32에서는 처리량과 지연이 함께 증가했다.** 처리량 약 37.9% 증가, p50 약 42.3% 증가, p95 약 35.0% 증가다. 서로 다른 대화 진행 깊이도 영향을 줄 수 있어 순수한 동시성 효과로 단정하지 않는다.
5. **슬롯 8→16의 추가 개선은 작았다.** 같은 C8·16·32에서 RPS는 각각 약 1.0%·1.2%·3.6% 증가했다. p95는 C8에서 약 0.5% 감소했지만 C16·32에서는 약 2.1%·0.8% 증가했다. 반복 검증 없이 성능 향상을 확정하지 않는다.
6. **슬롯 16, C64는 처리량 증가와 지연 악화가 함께 나타났다.** 5.903 req/s, 성공 E2E p95 21.788초이며 마지막 Grafana 화면에 Preemption Rate 0.00349 ops/s가 표시됐다. 클라이언트 오류 0건과 서버 preemption 발생은 구분한다.
7. **Grafana는 대기열 증가와 높은 GPU 사용률을 보여준다.** 캡처 범위와 이동 집계가 이전 실험을 포함한다. 슬롯 16의 간이 화면에는 1분·5분 집계가 함께 추가됐으며, 이를 실험 전체 백분위와 동일시하지 않는다.
8. **슬롯 16→32에서도 같은 C16·32·64의 처리량 개선은 뚜렷하지 않았다.** RPS 변화는 각각 +0.8%·-1.3%·+0.7%다. 슬롯 32의 C128은 8.573 req/s, E2E p95 31.212초였다. 연결 오류로 중단된 초기 C16·C128과 준비 실패는 비교에서 제외했다.
9. **TTFT는 캡처 카드의 관측 최저·최고만 별도 비교한다(§7.6).** 개별 요청의 최소·최대나 실험 전체 P99가 아니며, 초기 화면에는 이전 실험·실패 시도의 이동 집계가 섞일 수 있다.
10. **설정 슬롯 수는 실제 실행 수를 보장하지 않는다(§6.4).** 슬롯 여유·대기·높은 KV가 함께 관측됐지만, KV 용량과 토큰 예산의 기여도는 원시 지표·스케줄러 로그로 추가 확인해야 한다. 요약 후 슬롯 재비교는 미적용 검토안이다.

## 2. 무엇을 측정했는가

### 2.1 호출 범위

```text
Python 부하 발생기 → localhost:18000(port-forward) → vLLM
```

STT, 백엔드 애플리케이션, Redis, TTS, 프런트엔드를 거치는 서비스 전체 경로는 측정하지 않았다. 이 문서의 E2E는 **부하 발생기에서 vLLM 요청을 보내고 응답을 받기까지의 시간**이다.

### 2.2 실행 조건

| 항목 | 실제 실행/기록 내용 |
|---|---|
| 모델 | `qwen3-4b-fp8` |
| 실행 모드 | `accumulate-unbounded` |
| 주요 옵션 | `--unlimited --error-limit 10 --duration 300` |
| 요청 타임아웃 | 45초 |
| 기록된 문맥 길이 설정 | `context_length=4096` |
| 동시 요청 | 슬롯 1·2·4·8은 기본 1·2·4·8·16, 슬롯 8은 32 추가. 슬롯 16은 1·8·16·32·64, 슬롯 32는 1·16·32·64·128 |
| 대화 | 시나리오별 사용자 대본과 실제 모델 응답을 누적 |
| 부하 방식 | 각 작업자가 한 번에 요청 하나를 보내고, 완료되면 다음 요청을 보내는 폐쇄형 부하 |
| 워밍업 | 기존 구현 기준 `/health` 확인 후 `Hello world!` 요청 2회 순차 실행 |
| Pod 운용 | 사용자 설명상 같은 슬롯의 동시성 단계를 진행할 때 Pod를 재생성하지 않음 |

기존에 확인한 요청 구현은 `stream=false`, `max_tokens=128`, `temperature=0.7`, `top_p=0.8`, thinking 비활성화 설정을 사용했다. 이 항목들은 구현 기준이며 모든 실행의 실제 HTTP payload를 별도로 보관해 대조한 것은 아니다. `max_tokens=128`은 출력 상한이며 모든 응답이 128토큰이라는 뜻이 아니다.

`concurrency=N`은 동시에 응답을 기다리는 요청의 목표 수다. 초당 요청 수나 실제 서비스 사용자 수와 같지 않다. 느려지면 다음 요청도 늦게 발생하므로 고정 유입률 실험과도 다르다.

### 2.3 종료와 집계 규칙

- `--unlimited`는 대화 턴 수 제한을 풀지만 모델 문맥 한도, 실행 시간, 오류 중단 기준까지 제거하지 않는다.
- 오류 10회는 전체 작업자의 **누적 오류** 기준이다. 성공 응답이 나와도 누적 오류 수는 초기화되지 않는다.
- 중단 시 이미 진행 중인 요청을 정리하므로 최종 오류 수가 기준 10회를 넘을 수 있다(문맥 오류 11회, 제외한 슬롯 32 연결 오류 실행은 25·66회).
- `duration`은 측정 구간이다. `drain`은 구간 종료 후 진행 중 요청을 마무리하는 시간이다.
- 성공 RPS와 출력 TPS는 **측정 구간 안에서 완료된 성공 요청** 기준이다.
- 성공 E2E p50/p95는 **종료 후 정리 중 완료된 성공 요청도 포함**하고 실패 요청은 제외한다.
- 따라서 표의 전체 성공 수를 300으로 나눈 값과 기록된 RPS가 일치하지 않을 수 있다.
- `drain`만으로 부하 종료 후 시스템이 정상 상태로 완전히 회복됐다고 판정할 수는 없다.

## 3. 자료와 신뢰 범위

### 3.1 결과 출처

| 슬롯 | 정량 결과 출처 | 확인 수준 |
|---|---|---|
| 1 | 새 TXT 7개 중 최종 요약 5개 + C1 터미널 PNG 요약 1개 | TXT의 조회 슬롯 1 확인. 준비 실패 1개, C1 TXT는 최종 요약 누락. C16 A·B 모두 보존 |
| 2 | TXT 측정 결과 5개 + 준비 실패 1개 | 로그의 Pod 인자 조회 결과가 슬롯 2임을 확인 |
| 4 | TXT 측정 결과 5개 + 준비 실패 1개 | 로그의 Pod 인자 조회 결과가 슬롯 4임을 확인 |
| 8 | TXT 측정 결과 7개 + 준비 실패 1개 | 로그의 Pod 인자 조회 결과가 슬롯 8임을 확인. 동시 요청 1은 2회 수행 |
| 16 | TXT 측정 결과 6개 + 준비 실패 2개 | 로그의 Pod 인자 조회 결과가 슬롯 16임을 확인. 동시 요청 1은 2회 수행 |
| 32 | TXT 비교 채택 7개 + 연결 오류 종료 2개 + 준비 실패 2개 | 조회 슬롯 32 확인. C1은 3회 수행, 연결 오류 실행은 제외 |

성능 비교에 채택한 결과는 총 **36개**(TXT 최종 요약 35개 + 슬롯 1 C1 터미널 PNG 요약 1개)다. TXT 전체 46개는 최종 요약 37개, 준비 실패 8개, 최종 요약이 없는 C1 기록 1개로 구분된다. 요약 37개 중 슬롯 32의 연결 오류 실행 2개를 제외했다. 슬롯 1의 기존 PDF 결과 5개는 새 측정 6개로 교체해 비교에서 제거했다. 문맥 한도에 따른 조기 종료는 관측 결과로 유지하며, 채택은 오류 없이 300초를 수행했다는 뜻이 아니다.

슬롯 2 로그의 실험 이름은 `slots1`로 남아 있지만, 파일의 `S2`와 서버 Pod 인자 조회는 슬롯 2를 가리킨다. 이 문서에서는 **슬롯 2로 분류**한다. 인자 조회는 당시 kubectl 컨텍스트의 Pod 기준이며, `base_url`의 실제 대상과 동일한지 별도의 연결 추적까지 검증한 것은 아니다.

슬롯 32는 TXT 11개 중 비교 채택 7개(C1 3회, C16·32·64·128 각 1회), 준비 실패 2개, 측정 중 연결 오류 종료 2개다. 모든 파일의 조회 슬롯 수는 32다. 실패한 첫 시도를 제외하라는 요청은 연결 오류 실행에 적용했으며, 정상적인 문맥 한도 실험을 임의로 버리지 않았다.

### 3.2 실행 간 공통성과 차이

- 슬롯 1·2·4·8·16·32 TXT의 대본 SHA256은 모두 같다.

```text
8da7eb02b5bb151757a0740f88f20c8193819ef539250624479b56ff27fcc78d
```

- 새 슬롯 1 TXT에서도 위 전체 SHA256을 확인했다. C1의 최종 결과 숫자는 TXT에 없어 터미널 PNG에서 전사했다.
- 슬롯별 TXT에서 조회된 Pod는 각각 다음과 같다.

| 슬롯 | Pod |
|---|---|
| 1 | `vllm-qwen-bb9c66584-tmxzs` |
| 2 | `vllm-qwen-6f99fb76c9-qhbh7` |
| 4 | `vllm-qwen-684b9cbf77-d7kgd` |
| 8 | `vllm-qwen-dbbfcc4b9-kvfsn` |
| 16 | `vllm-qwen-54c7847674-94k8x` |
| 32 | `vllm-qwen-f9b7f6f76-hsmsc` |

같은 슬롯 내 Pod 이름이 유지됐어도 컨테이너 재시작 여부까지 증명되지는 않는다. restart count와 시작 로그가 없으므로 캐시가 항상 유지됐다고 단정하지 않는다. 실행 순서, prefix cache 상태, 문맥 깊이, 출력 길이 차이는 비교의 교란 요인이다.

모두 동일한 동시 요청 수의 최종 TXT 요약을 비교했다. 변화율은 `(슬롯16 / 슬롯8 − 1) × 100`이며 지연의 양수는 증가를 뜻한다.

C1의 슬롯 8 p95는 0.731/0.865초, 슬롯 16은 0.679/0.680초였다. 낮은 부하에서 뚜렷한 지연 악화는 이 실행들에서 관측되지 않았다. 다만 실행별 캐시·문맥·출력 길이가 통제된 반복 비교가 아니므로 슬롯 증가 자체가 p95를 개선했다고 확정하지 않는다.

슬롯 16에서 C32→64는 RPS 약 40.2%, 출력 TPS 약 43.0% 증가와 함께 p50 약 36.4%, p95 약 38.2% 증가를 보였다. C64의 같은 동시성 슬롯 16→32 비교는 §5.6에 추가했다. 이 결과로 최대 지속 처리량이나 운영 수용 인원을 확정하지 않는다.

## 6. 오류와 지연을 함께 해석하기

### 6.1 저동시성의 문맥 한도 오류

성능 비교에 채택한 실험에서 기록된 요청 오류는 문맥 한도 초과(`CONTEXT_LIMIT_EXCEEDED`)였다. 실패 요청을 성공 E2E 백분위에서 제외하므로 짧은 p95와 오류가 동시에 나타날 수 있다.

응답이 빠른 저동시성 작업자는 같은 시간 안에 더 많은 턴을 진행한다. 초기화 없이 대화를 누적하면 입력 길이가 모델 한도에 더 일찍 도달할 수 있다. 슬롯 8, 동시 요청 2에서는 카페 사용자가 119턴까지 성공한 뒤 120턴부터 문맥 오류가 기록됐다.

실패한 사용자 입력도 누적되는 구현에서는 이미 너무 길어진 문맥으로 재요청해 오류가 연속 발생할 수 있다. 오류 10회가 서로 다른 사용자 10명의 독립 실패라는 뜻은 아니다.

### 6.2 고동시성에서 오류가 없었던 의미

성능 비교에 채택한 동시 요청 8·16·32·64·128 실행은 300초 종료까지 문맥 한도 오류가 기록되지 않았다. 하지만 작업자별 진행 턴 수가 줄어 문맥 한도에 도달하지 않았을 가능성이 있다. 이를 고동시성의 안정성이 더 높다는 증거로 사용하지 않는다.

슬롯 8의 동시 요청 16과 32는 각각 성공 900건, 1,251건이고 오류는 0건이다. 같은 조건의 p95는 11.592초와 15.646초다. **오류율과 응답 시간을 함께 봐야 한다.**

### 6.3 타임아웃 및 종료 사유

최종 결과 요약에서 클라이언트 타임아웃과 HTTP 408·504 응답은 모두 0회였다. 저동시성의 `error_limit` 종료와 고동시성의 `duration` 종료를 구분해 기록했다. 서버 로그 전체를 확보한 것은 아니므로 이 사실만으로 모든 내부 오류나 재시작이 없었다고 보증하지 않는다.

`finish_reason=length`는 정상 응답의 출력 길이 상한 종료이며, 입력 문맥 오류와 다르다. 예를 들어 슬롯 2의 동시 요청 2에서는 2회, 동시 요청 4에서는 1회 기록됐다. 오류 수와 합치지 않는다.

### 6.4 슬롯이 남아도 처리 요청이 줄고 대기가 생기는 이유

**검토 결론:** `max_num_seqs=8`은 실행 시퀀스 수의 상한이며 8건의 실행을 항상 보장하지 않는다. 대화 누적 뒤 실행 수가 감소하면 KV 공간과 스텝당 토큰 예산을 함께 확인한다. 예로 든 `슬롯 8·동시 요청 8·running=4·waiting=4`는 해당 시점의 원시 지표를 확보하지 못해 원인을 확정하지 않는다.

#### 실측 근거와 확인 범위

| 조건 | 관측 | 출처·한계 |
|---|---|---|
| 슬롯 8, C16 | 간이 화면에 `running=6, waiting=10`; 같은 실험에서 KV 94.3% 관측 | §7.2. 두 값을 정확히 같은 시점의 값으로 결합하지 않음 |

실행 수가 설정 상한 미만인데도 대기가 있는 관측은 확인됐다. 높은 KV 사용률을 동반한 사례는 **KV 용량 제약 가설과 부합**한다. 다만 높은 점유율 하나로 새 요청의 할당 실패를 입증할 수는 없다. 할당 가능한 블록, 재사용·회수 가능한 prefix cache, 실제 요청 길이와 스케줄러 판단을 추가 확인해야 한다.

#### 가능한 동작 — 공식 문서와 연결

- **KV 공간:** 전체 이력을 재전송하는 누적 대화에서는 문맥이 길어진다. 같은 모델·KV dtype에서 저장해야 할 토큰이 늘면 KV 요구량도 증가한다. Prefix 공유 등으로 실제 점유량은 달라지므로 `KV 사용량 / running`을 요청당 문맥 길이로 환산하지 않는다. KV 부족 시 선점·재계산이 가능하다는 동작은 [vLLM v0.32.0 Preemption](https://docs.vllm.ai/en/v0.32.0/configuration/optimization/#preemption)을 참고한다. 선점 0은 메모리 여유의 증명이 아니며, 선점이 시작될 때까지 기다려야 병목을 판정할 수 있는 것도 아니다.
- **토큰 예산:** 실험 설정 `max_num_batched_tokens=512`는 한 스텝의 처리 예산이며 요청 전체 입력 길이 제한이 아니다. Chunked prefill은 decode를 우선하고 남은 예산으로 prefill을 나눠 처리한다. 슬롯 여유만으로 새 요청이 즉시 모두 들어간다고 가정할 수 없다. [vLLM v0.32.0 Chunked Prefill](https://docs.vllm.ai/en/v0.32.0/configuration/optimization/#chunked-prefill). 이것이 해당 캡처의 직접 원인이었다는 스케줄러 추적은 확보하지 못했다.
- **관측 시점:** 요청 완료·교체 순간과 scrape 간격도 일시적인 실행 수 감소에 영향을 줄 수 있다. `running`은 실행 상태의 요청 수이며 매 스텝에서 실제 연산한 요청 수와 동일시하지 않는다. 메인 스택 그래프 상단선과 원계열, 이동 최대값과 순간값을 구분한다.

| 같은 시각에 확인할 상태 | 우선 검토 | 추가 확인 |
|---|---|---|
| 실행 수 < 슬롯 상한, 대기 > 0, 높은 KV 점유 | KV 용량 제약 가설 | 할당 블록·요청 길이·캐시 재사용 및 스케줄러 로그 |
| 실행 수 < 슬롯 상한, 대기 > 0, KV 여유 | 토큰 예산·prefill 스케줄링 등 | 실제 스텝별 처리 토큰과 대기 사유 |
| 실행 수 감소가 짧게 나타나고 회복 | 완료·교체와 수집 시점 영향 | 같은 Pod의 같은 시각 원계열을 반복 확인 |

`입력 tok/s`는 처리 속도다. 이것만으로 요청당 입력이 길었다고 판정하지 않는다. 요청당 `prompt_tokens` 또는 입력 길이 분포가 필요하다. 대기 원인은 실제 사용 버전의 메트릭·라벨과 로그로 확인하며 특정 이름의 지표가 항상 제공된다고 가정하지 않는다.

#### 서비스 설계에 주는 의미 — 아직 적용하지 않은 검토안

슬롯 확대는 실행 수 상한을 높이고, 요약은 요청의 문맥을 줄인다. 긴 문맥으로 KV가 제약인 조건에서는 슬롯만 늘리는 효과가 제한될 수 있다. **요약 적용 후 슬롯 4·8·16을 다시 비교**하며, 슬롯 4는 현재 단회 결과에 따른 초기 비교 후보로 둔다. 확정 운영값이나 수용 사용자 수로 기록하지 않는다.

요약 시점은 고정 턴 수 대신 실제 토큰 수로 정하고, 교정 리포트용 원문은 보존하면서 LLM 전송 이력만 압축하는 방향을 검토한다. 같은 GPU의 요약 작업도 부하에 포함해야 한다. 요약으로 prefix가 바뀌면 캐시 재사용도 달라질 수 있어 성능 개선을 보장하지 않는다.

다음 검증은 입력 길이·출력 조건을 맞춘 상태에서 요약 전후를 비교한다. 요청별 입력/출력 토큰, 같은 시각의 실행·대기·KV, 선점 카운터 증가량, 가능하면 스케줄러 대기 사유, 초반·후반 E2E p95·TTFT와 요약 비용·사실 보존 품질을 함께 기록한다. Context 4096 초과 오류와 동시 요청 간 KV 용량 제약은 별도 원인으로 분류한다.

### 7.3 대시보드 통계 해석 시 주의점

1. **5분 이동 집계의 실험 혼합:** `rate(...[5m])`는 각 평가 시점 이전 5분을 사용한다. X축을 실험 시작–종료로 맞춰도 초반 값에는 이전 실험이 섞일 수 있다. 고정 시간 범위만 지정하는 것으로 완전히 해결되지 않는다.
2. **백분위 시계열의 평균:** 범례의 `Mean`이 P95/P99 시계열 평균이면 실험 전체 요청의 P95/P99가 아니다.
3. **히스토그램 패널:** 캡처의 `histogram_quantile(... rate(..._bucket[5m]))` 결과를 Histogram으로 그린 패널은 시간별 백분위 값의 분포다. 요청 원자료의 지연 분포와 다르다.
4. **TTFT/TPOT와 클라이언트 E2E:** 서버 TTFT에는 서버 관점의 대기와 첫 토큰까지 시간이 반영된다. 현재 비스트리밍 클라이언트 결과에서 개별 요청 TTFT/TPOT를 직접 측정한 것은 아니다.
5. **Success Rate 100%:** 쿼리 원문을 확인하지 않은 패널의 100%를 모든 HTTP 요청 성공률과 동일시하지 않는다. 생성 전 검증에서 거절된 HTTP 400이 집계되지 않을 가능성을 확인해야 한다.
6. **System Efficiency:** 패널 이름만으로 GPU 연산 효율을 뜻한다고 해석하지 않는다. 실제 PromQL과 분모·분자 확인이 필요하다.
7. **누적/스택 그래프:** Scheduler State의 노란 상단선이 스택 합계일 수 있다. 대기 요청 수는 범례·원계열로 확인한다.
8. **카운터와 기간:** Finish Reason Distribution의 `stop` 수, warmup 포함 카운터, TXT 성공 수는 집계 범위가 다를 수 있어 직접 일치시키지 않는다.
9. **버킷 정밀도:** 특정 값 부근에 백분위가 오래 머물거나 급변하는 현상은 원시 버킷 경계와 쿼리를 확인해야 한다. 화면만 보고 특정 임계값에 정확히 제한된다고 단정하지 않는다.

- **C64 통계 차이:** 같은 마지막 메인 화면의 TTFT P99는 19.8초, E2E P99 시계열 최대는 29.8초다. TXT 성공 요청에서 출력된 최대 E2E는 26.97초, 전체 성공 p95는 21.788초다. 이동 창·버킷 보간·집계 범위가 다른 값이므로 같은 통계로 섞지 않는다.
- 슬롯 16 고부하 간이 화면은 GPU 100%와 VRAM 약 7,093 MiB를 표시한다. 이 값은 캡처 시점의 관측이며 전체 실험 평균을 의미하지 않는다.

지표가 0으로 내려갔다 다시 증가하는 구간은 실행 사이 공백과 인접한다. 이것만으로 Pod 재시작이나 장애 복구를 단정하지 않는다. TXT의 Pod 이름은 동일하지만 컨테이너 restart count는 별도 확보하지 않았다.

## 9. 후속 검증 제안 — 아직 수행하지 않음

1. 서비스 목표 지연(p50/p95/TTFT)과 허용 오류율을 먼저 정한다.
2. 슬롯 4·8·16·32를 같은 조건에서 반복하고 순서를 바꿔 실행한다. Pod/캐시 유지 여부를 실험 조건으로 명시한다.
3. 현재의 누적 대화 실험은 유지하되, 별도 실험에서 입력·출력 길이를 통제해 순수 처리 성능을 비교한다. 대화 초기화 모드는 이번 실험에 포함되지 않았다.
4. 각 요청의 시작·종료·입출력 토큰 수·오류 사유를 보관한다. TTFT가 필요하면 스트리밍 측정을 별도로 설계한다.
5. Grafana 쿼리, histogram 버킷 경계, scrape 간격을 확보한다. 실험 전체 통계는 해당 기간의 원시 요청 또는 버킷 증가량으로 계산하고 경계 오차를 명시한다.
6. Pod restart count와 서버 로그를 함께 수집하고, 서비스 전체 경로의 부하 실험은 별도로 수행한다.
